    Changelog¶

    All notable changes to this project are documented here.

    The format is based on Keep a Changelog and the project follows Semantic Versioning. See VERSIONING.md for how the adapter version maps to SAP CPI iFlow compatibility.

    [Unreleased]¶

    Fixed¶

    • Sender with DLQ: a failed dead-letter write is now visible in the CPI monitor. Up to 1.4.2 the MPL entry showed only the integration flow's error, and the reason why the DLQ write failed was in the tenant trace alone. The entry now carries KP-DLQ-001, a status text that leads with the failed write and its root cause (dead-letter write to <topic> failed: <class>: <message> (original: …)), a --- DLQ Error --- section with its full stack trace in the KafkaAdapterError attachment, and a hint for well-known causes (record without key on a compacted DLQ topic, missing WRITE, missing topic, record too large). This applies to failed flow processing, deserialization and JSON Schema validation (#289).
    • Sender: every failure is reported once by the adapter. A failed record after its retries, a failed batch without DLQ and a failed deserialization each wrote a second adapter MPL entry with the same error (#289).
    • Sender in batch mode with DLQ: a failed batch of one record no longer runs through the integration flow a second time. Its batch run counts as the record's first attempt, so a permanent error sends it straight to the DLQ and a transient one continues with its retries (#289).
    • A record the broker rejects (InvalidRecordException, e.g. a record without key on a compacted topic) is classified as a data error. The DLQ producer and the receiver's producer are no longer rebuilt for it, since a fresh producer is rejected the same way (#289).

    Changed¶

    • Sender: a failure of the integration flow is reported with the new error code KP-FLOW-001 (iflow.processing_failed) instead of KP-GEN-001, in the MPL (KafkaAdapterErrorCode, status text) and in the tenant trace. Monitoring or alerting that matches KP-GEN-001 for flow errors needs to match KP-FLOW-001 (#289).
    • Sender in batch mode: a record that fails JSON Schema validation is reported with KP-CFG-002, as in single mode, instead of KP-GEN-001. With DLQ, its MPL entry carries the DLQ outcome (MOVED), SAP_Sender and SAP_Receiver (#289).
    • Sender: MPL entries with a DLQ outcome set SAP_Sender to the source topic and SAP_Receiver to the DLQ topic, and carry the new custom header properties KafkaAdapterOriginalErrorCode, KafkaAdapterDlqOutcome (MOVED/SEND_FAILED) and KafkaAdapterDlqTopic (#289).

    Dependencies¶

    • snappy-java 1.1.10.8 → 1.1.10.12 (shipped in the adapter bundle) and zstd-jni 1.5.7-21 → 1.5.7-23 (tests only); replaces Dependabot #270 and #269.

    [1.4.2] - 2026-10-16¶

    Added¶

    • The start line class-warmup.start, written once per adapter version when its first Kafka endpoint starts, now names the runtime: java (Java version), javaVendor and camel (Camel version). SAP's adapter development documentation still names Java 8, while the adapter needs Java 11 or later; the README now says so. See issue #251.
    • CI scans what the adapter ships for known vulnerabilities. The new Dependency Scan workflow builds the adapter bundle and checks it with Grype, including every library on its Bundle-ClassPath and kafka-clients, whose classes the bundle holds unpacked, so libraries that only arrive transitively are covered too. It fails on a finding of severity high or critical and runs on pull requests that change pom.xml, on main and weekly. The bundle of 1.4.1 would have failed it with the LZ4 codec of issue #240 (GHSA-vqf4-7m7x-wgfc, high). Static analysis was already running: CodeQL checks every pull request as GitHub code scanning, which CONTRIBUTING.md now describes. See issue #250.

    Changed¶

    • Internal refactoring, no change in behaviour, configuration or log output: the receiver's node-fault escalation (producer.node.fault.escalation, with its JVM state and, at diagnostics level FULL, a thread dump) moved from CpiKafkaPlusProducer into its own class NodeFaultEscalation. The event still logs under the CpiKafkaPlusProducer logger category.
    • Internal refactoring, no change in behaviour, configuration or log output: the member suffix from CF_INSTANCE_INDEX or HOSTNAME (used in the sender's group.instance.id and the receiver's transactional.id) and the topic hash in transactional.id now come from one class, NodeIdentity, instead of CpiKafkaPlusConsumer and CpiKafkaPlusProducer. The ids stay the same.
    • Internal refactoring, no change in behaviour, configuration or log output: the transaction slots of the receiver's transactional batching, the transactional.id each slot stands for and the create/close of the per-attempt producer moved from CpiKafkaPlusProducer into their own class TransactionalProducerPool. The ids and the wait for a free slot stay the same, and the start-up lines still log under the CpiKafkaPlusProducer logger category.
    • Internal refactoring, no change in behaviour, configuration or log output: the receiver's topic check (whether the target topic exists, at start-up and before every send) and the metadata pre-warm of its Kafka client moved from CpiKafkaPlusProducer into their own class TopicMetadataChecker. The probe's timeouts, the re-checks of a missing topic and the topics it remembers stay the same, and it still logs under the CpiKafkaPlusProducer logger category.
    • Internal refactoring, no change in behaviour, configuration or log output: the sender's check whether a failed record is transient moved from RecordProcessor into KafkaErrorHelper, which already classifies the receiver's send errors. It decides which failures Skip Retries for Permanent Errors (retryOnlyTransientErrors) still retries before the DLQ and fills the retryable field of adapter.failure.reported; the errors that count as transient stay the same.
    • Internal refactoring, no change in behaviour, configuration or log output: the start-up checks that reject a configuration at deployment moved from CpiKafkaPlusProducer and CpiKafkaPlusConsumer into ReceiverConfigValidator and SenderConfigValidator. The checks run in the same order with the same messages; the receiver still checks its transaction and retry settings after the start-up line, and the lines logged between the checks keep their place and their CpiKafkaPlusProducer and CpiKafkaPlusConsumer logger categories.
    • Internal refactoring, no change in behaviour, configuration or log output: the sender's decision what kind of failure a failed poll is (credentials, permissions or certificates rejected, a static group member fenced, the class space replaced by an adapter update, or anything else) moved from CpiKafkaPlusConsumer into its own class PollFailureClassifier. The regular poll and the keep-alive poll now both take the kind from there instead of each repeating the checks; the checks run in the same order, and what each poll does with each kind stays the same.
    • Internal refactoring, no change in behaviour, configuration or log output: the sender's decisions about a failed record or batch moved from RecordProcessor into their own class RecordFailurePolicy: whether a record is retried within the poll (Max Retries before DLQ, Skip Retries for Permanent Errors), written to the DLQ, retried later or skipped (Error Handling), whether a failed batch is processed record by record, and that a JSON Schema-invalid record is dropped without a DLQ. RecordProcessor still writes to the DLQ, traces, reports to the MPL, commits and waits between retries, and skipping or blocking a single record and a whole batch now share one implementation.
    • Sender and receiver UI: the retry fields use the same words in both directions. The sender's Max Retries before DLQ is now Retries before DLQ (additional attempts), since it counts the retries after the first attempt (3 means up to four attempts), and Skip Retries for Permanent Errors is now Retry Transient Errors Only, the name the receiver already uses for the same switch. The receiver's Max Send Attempts is now Send Attempts (total, 1 = off), since it counts every attempt including the first. Only the labels and texts change; saved values keep their meaning. See issue #257.
    • Sender UI: the tooltips of the batching, offset and commit fields say what the integration flow actually gets. Batch Mode says that the flow receives an envelope with up to Max Records per IFlow Run (MPL) records of one partition ({"kafkaRecords":{"record":[…]}} or the XML equivalent) instead of the message body, and Batch Output Format shows that envelope instead of a bare JSON array. Max Records per IFlow Run (MPL) says that a batch never spans partitions or polls, so a value above Max Poll Records has no effect. Auto Offset Reset says when it applies (a new Consumer Group ID, group offsets the broker deleted after 7 days without an active consumer by default, a committed offset the topic's retention deleted) and that Latest then never reads the older messages. The option Auto Commit (Periodic) is now labelled Auto Commit (Periodic, may lose messages): polled records that were not processed yet can be committed and lost, for example when the flow is stopped during a long IFlow call. Its tooltip and the one of Drain Backlog say that the two cannot be combined. See issue #252.
    • Receiver and sender UI: texts that contradicted the start-up checks are corrected. The Subject Name Strategy options RecordNameStrategy and TopicRecordNameStrategy are now labelled (not supported – deployment fails), and the tooltip says that together with Serialize Values as Avro they fail the deployment, as they do since 1.4.1, instead of saying that every message fails; both values stay selectable so that saved configurations remain valid. Delivery Timeout (Seconds) says that its maximum of 870 seconds applies only to transactional batching (Enable Transactions with Batch Send Mode JSON Array or XML List), not to every channel with Enable Transactions switched on. Buffer Memory (KB) says that, with a full buffer, a send waits at most 30 seconds (or the delivery timeout, if that is shorter) for free space and then fails. The input hints of the receiver's Producer Batch Size (KB) and the sender's Poll Timeout (ms), Fetch Min Bytes and Fetch Max Wait (ms) no longer ask for a positive number, since 0 is accepted. See issue #253.
    • Sender UI: the tooltip of Consecutive Error Threshold (Auto-Pause on Errors) says what counts as a failure. A record counts once, after its last attempt, also when it is then written to the Dead Letter Queue, so five dead-lettered records in a row pause the consumer with the default threshold; without a DLQ a failed batch counts once, and with Retry Failed Message every new attempt on a later poll counts again. Records that fail JSON Schema validation do not count, and a successful record or batch resets the count. The documentation said that every failed IFlow call counts, which overstated the retries before the DLQ. The counting itself is unchanged. See issue #258.
    • Sender and receiver UI: the tooltip of SSL Keystore Alias says what an alias does to trust. As soon as any alias is set, the adapter trusts the certificates of the whole CPI tenant keystore instead of the JVM default truststore, so the broker's CA certificate (or its self-signed certificate) must be in the tenant keystore, also for a broker with a publicly trusted certificate; for client-certificate authentication (mTLS) the alias must name a key pair. The authentication guide now says that the field takes the alias of an entry in the tenant keystore, not the name of a keystore. The behaviour is unchanged. See issue #256.
    • Documentation: pages that contradicted the code are corrected. Troubleshooting: the node-fault escalation example shows a fault that can escalate (only failures classified FATAL_PRODUCER_UNUSABLE or UNKNOWN_FATAL count, a timeout never does), successful sends do not reset its 20-minute window, and diagnostics level FULL only adds a thread dump to that escalation, so it costs nothing on a normal send. Kafka Headers and Dead Letter Queue: the batch headers apply with Batch Mode, CpiKafkaPlusBatchOutputFormat is JSON_ARRAY or XML_LIST, the record-by-record fallback of a failed batch sets CpiKafkaPlusFallbackMode, a message without kafka.OVERRIDE_TIMESTAMP gets the client's send time (the broker's only on a LogAppendTime topic), CpiKafkaPlusDlqErrorType is set for failed IFlow calls only with Retry Transient Errors Only switched on, CpiKafkaPlusDlqRetryCount counts the retries (attempts − 1) including one that failed permanently, and the DLQ topic is always on the main cluster. FAQ: the message size limit applies to each Kafka record, not to a whole batch. Configuration: required and conditionally required fields are marked (required) with their condition. Getting Started names the adapter as KafkaAdapterPlus, and ADR 0001 and ADR 0004 carry dated notes on the transactional.id format and the heartbeat level. See issue #254.
    • Deployment errors now name the field as the CPI UI shows it, its parameter and the value it got, all in one form: '<UI label>' (<parameter>) must …, got: <value>, for example 'Send Attempts (total, 1 = off)' (producerRetryMaxAttempts) must be between 1 and 5, got: 6 instead of Please set producerRetryMaxAttempts between 1 and 5 (configured value: 6). Most start checks named only the parameter, which the UI does not show, and some named no value at all. A text value is quoted, so an empty value or spaces around it show. Two receiver lines about the retry settings are now ERROR producer.config.ineffective instead of WARN, which does not reach the tenant trace: Send Attempts (total, 1 = off) above 1 on a batch channel without transactions, and with a single transaction slot. The sender now also logs consumer.config.clamped for an Initial Pause Duration (sec) above 900 seconds, which was used as 900 without a line. No configuration is rejected that deployed before. Rollout note: a search or alert on the old message texts has to be adapted. See issue #255.
    • Sender and receiver UI: the tooltips of Consumer Group ID and Transactional ID Prefix say that each integration flow and tenant needs its own value. The sender joins its consumer group with static membership as <Consumer Group ID>-<worker index>, so two channels with the same group ID, for example a copied integration flow or two stages on one Kafka cluster, fence each other with FencedInstanceIdException and both stall; two transactional receivers with the same prefix and topic fence each other's transactions in the same way. The Consumer Group ID tooltip no longer says that every instance sharing a group ID takes a share of the partitions. The FAQ and the code comments no longer claim that the consumer sends a LeaveGroup when it stops or misses max.poll.interval.ms: as a static member it sends none, and the broker keeps its partitions until session.timeout.ms (30 s) has passed. The deployment error for a Polling Interval (Seconds) above 21600 now says that the consumer would drop out of its group between polls. Troubleshooting explains poll: FencedInstanceIdException. The IDs themselves are unchanged. See issues #193 and #194.

    Fixed¶

    • Sender with Auto-Pause on Errors: records could be skipped after an auto-pause. While the channel is paused, a keep-alive poll keeps it in the consumer group; when a rebalance assigned a partition during that poll, the poll returned the partition's records and the consumer moved past them without processing them. They are now rewound, as the regular keep-alive poll already did, so the next poll after the pause reads them. Both keep-alive polls now share one implementation (KeepAlive). See issue #230 (N-D-1).
    • Sender: a failed record whose exception cause chain loops back on itself (A → B → A, which Throwable.initCause allows, for example when a script wraps the exception that triggered its retry) kept the poll thread spinning forever: 100 % CPU, no log line, deaf to an interrupt, alive after undeploy, and the next node hung on the same record after the rebalance. Every walk over a cause chain now stops at a cause it has already seen (and after 64 links), so such a record is retried, dead-lettered or skipped like any other failed record. See issue #241.
    • Sender: a record whose route call failed while the integration flow was being stopped or undeployed was treated like a broken record. The stop interrupts the poll thread, the route call then fails because of the interrupt, and the record was dead-lettered with CpiKafkaPlusDlqErrorType=PERMANENT, or skipped and committed with Skip Failed Message; a failed batch was skipped as a whole. Such a record (or batch) now stays uncommitted and is delivered again after the restart, and the failure is neither reported to the MPL nor counted for Auto-Pause on Errors. A graceful shutdown no longer starts the next record of the poll either: it lets the record in flight finish and stops then, instead of working through the rest of the poll, which could outlast the shutdown timeout and end in an interrupted route call. See issue #242.
    • Sender: failures of the keep-alive polls no longer go unnoticed. During an Auto-Pause on Errors cooldown the keep-alive poll logged every failure at DEBUG only, so rejected credentials or permissions and a fenced static member stayed hidden for up to 15 minutes behind the status "Auto-paused after … consecutive processing failures". Between two emit cycles the keep-alive poll left a Java Error unclassified, such as the NoClassDefFoundError of an adapter update, so in SCHEDULED mode only the next emit cycle, up to hours later, stopped polling. Both keep-alive polls now handle a failure like the regular poll: rejected credentials, permissions or certificates stop polling until a redeploy, a fenced static member cools down, a replaced class space stops polling (poll.bundle-wiring-invalid), and any other Error is logged at ERROR and counts towards a reconnect. Other failures during the cooldown are logged at WARN, at most once a minute. See issue #243.
    • Sender: three diagnostics reported the wrong thing. CpiKafkaPlusDlqRetryCount and the trace's retryAttempts left out the retry that failed with a permanent error, so a record that failed transiently and then permanently on its first retry reported 0 retries instead of 1. consumer.partition.retry named the record that blocked the partition, not the offset the partition is rewound to, which can be an earlier record of the same poll, for example a failed batch in front of a record whose DLQ write failed. It now names the offset the partition resumes at and adds blockedAt when the two differ, and the retry delay keeps doubling for as long as the partition resumes at the same offset. When the keep-alive poll or an extra drain cycle sought its partitions back to records it had not processed and one seek failed, the partitions after it were not sought back at all, behind a misleading WARN "records may be re-polled on next cycle anyway". Each partition is now sought back on its own. A failed seek back on a partition the consumer still holds, there or after a regular poll, is logged at ERROR (consumer.rewind.failed), because the partition stays past records that were not processed and the next commit can pass them; a partition revoked meanwhile is still only warned about, since its new owner starts from the committed offset. See issue #244.
    • Sender: the MPL status text of a failed record named its retries off by one. After exactly one retry it carried no retry hint, and a record that was tried only once read (after 0 retry attempts). It now reads (after 1 retry attempt) after one retry and names no retries when there were none. See issue #277.
    • Sender: a poll could keep the consumer from calling poll() again within max.poll.interval.ms, which is 10 minutes with Streaming (Continuous) and Polling Interval (Seconds) plus 10 minutes with Scheduled Polling. Retries before the dead-letter topic run on the poll thread, so long Retry Delay (Seconds) values, a slow or hanging integration flow and several failing records in one poll could add up past it: with the defaults (3 retries, no delay) and a backend that times out after 30 seconds, six failing records were enough. Kafka then gave the partitions to another member, which processed the same records again while this one was still working on them. The adapter now starts no record, batch or retry later than halfway through max.poll.interval.ms after a poll and leaves the rest of the poll to the next one (consumer.poll.timeLimit). A record whose next retry would start later does not wait for it on the poll thread: its partition is rewound to the record and paused until the retry is due, the other partitions keep flowing, and the next poll of the partition runs that retry instead of starting the record over (consumer.retry.deferred). Rollout: such records reach the integration flow or the dead-letter topic later, but after the same number of retries; a single flow call that takes longer than half of max.poll.interval.ms can still exceed it. See issue #192.
    • The adapter bundle shipped files it should not and missed files it should have. Every *.txt file of the build's working tree ended up in it (for example requirements-docs.txt, test resources and copies under target/), because the licence list was generated into the project root, while neither the adapter's LICENSE and NOTICE nor those of the Apache Kafka clients, whose classes the bundle contains unpacked, were in it. The bundle now ships LICENSE, NOTICE and the licence list THIRD-PARTY.txt under META-INF/, Kafka's LICENSE and NOTICE under META-INF/kafka-clients/, and no other stray files. It also left out Kafka's kafka/kafka-version.properties, so the Kafka clients logged the WARN Error while loading kafka-version.properties and reported their version as unknown, in their own log lines (Kafka version: unknown) and to the broker. They now report 4.3.1. See issue #249.
    • Receiver with Batch Send Mode XML List (XML_LIST): a <value> with child elements was written to Kafka as its elements only. Text next to them was lost (<value>Preis: <b>10</b> EUR</value> became <b>10</b>), and so were CDATA sections, comments and processing instructions. Namespaces declared on <kafkaRecords>, <record> or <value> were dropped: under <kafkaRecords xmlns:ns="urn:x" xmlns="urn:d">, <value><ns:order>1</ns:order></value> became <ns:order>1</ns:order>, which a namespace-aware consumer cannot parse, and an attribute with such a prefix failed the batch. A top-level element called html without a namespace was written as HTML: <br/> became <br>, which no XML parser reads, a META element was added to <head>, and the value was indented. The whole content of the value is now written as XML, and each top-level element of the value declares the namespaces in scope there, the default namespace included: <ns:order xmlns:ns="urn:x" xmlns="urn:d">1</ns:order>. The record value written to Kafka changes only for values with child elements, and only where they mix text and elements, have CDATA, comments or processing instructions next to their elements, sit under namespace declarations on <kafkaRecords>, <record> or <value>, or have a top-level html element. Every other value is written byte for byte as before, including text-only values, the indentation between elements, which is still dropped, and namespaces declared inside the value. A namespace prefix that is declared nowhere in the document now fails the batch as an XML parse error instead of being sent as it was. See issue #247.
    • Receiver: an exchange header with a byte[] value is written to Kafka as it is. Up to 1.4.1 the record header carried its text form, such as [B@1b6d3586. See issue #195.
    • Receiver: a message sent while the shared Kafka producer was being rebuilt after another message's failure could fail with a NullPointerException, or with "Cannot perform operation after producer has been closed" classified UNKNOWN_FATAL, which asked for one more rebuild, counted towards producer.node.fault.escalation and, with Send Attempts (total, 1 = off) above 1, stopped the retry (stopReason=PERMANENT). Each send attempt now takes the producer of that moment and builds a new one if the rebuild has discarded it. A send whose producer is closed under it fails as RETRIABLE, with "The shared Kafka producer was closed while this send was using it …" in front of Kafka's message, and neither rebuilds the producer again nor counts towards the escalation; with Send Attempts (total, 1 = off) above 1, a single message that Kafka refused before buffering it is sent again on the new producer. producer.rebuild.outcome reported producerRecreated=false for every rebuild, because the rebuild only discards the producer and the next send builds the new one; the line now carries producerDiscarded and consequence='the next send builds a new producer' instead. A serialization helper that could not be created, for example the Avro serializer with a Schema Registry credential alias that does not resolve, made every message build and close a complete Kafka producer before it failed; the helpers are now created first. With Batch Send Mode None (Single Message) and Enable JSON Schema Validation, a message whose body was a stream was validated and then sent empty, with Avro value serialization as a tombstone, and still got CpiKafkaPlusStatus=OK; the body is now read once, and the bytes that are validated are the bytes that are sent. The metadata pre-warm could report producer.metadata.prewarm outcome=FAILED with a NullPointerException when a rebuild cleared the producer meanwhile, and a pre-warm that finished on a replaced producer counted for the new one, which was then never pre-warmed for that topic; a pre-warm overtaken by a rebuild is now only logged at INFO and counts only for the producer it ran on. The cause of an inconclusive topic probe that a send error adds ("The broker could not be reached during the pre-send check either …") was kept per channel instead of per topic: with several topics, one topic's failed probe was added to another topic's send error, and confirming any topic removed it. It is now kept per topic. A message that still reached the receiver after the integration flow had stopped it built a new Kafka producer that nothing closed again. After the stop no producer is built until the next start: such a message, and the retry of a message whose producer the stop closed, fails with "The receiver for Kafka topic '…' was stopped (the integration flow is stopping or was undeployed), so no new Kafka producer is built and the message is not sent." See issue #246.
    • Sender: a channel with Enable Dead Letter Queue switched on no longer fails to deploy because of its Error Handling value. The field is hidden while the DLQ is on, and the DLQ then decides what happens to a failed record, but a value other than RETRY or SKIP (for example from an externalized parameter) was still rejected at deployment and could only be corrected after switching the DLQ off. Without a DLQ such a value is still rejected, and the message now names the field as the UI shows it: 'Error Handling' (errorHandling) must be RETRY (Retry Failed Message) or SKIP (Skip Failed Message), got: …. See issue #264.
    • Receiver with transactional batching: the length check of the transactional.id now covers every transaction slot. It checked the first slot only, so from 11 Max Concurrent Transactions on, the id of the later slots could be a character longer than the 249 characters the adapter allows. The message now names the field, gives the longest prefix that fits and says by how many characters to shorten it; it no longer says "under 249 characters", since exactly 249 are accepted. Rollout note: this can stop a receiver channel that deployed before, one with 11 or more Max Concurrent Transactions and a Transactional ID Prefix within one or two characters of the limit; shorten the prefix as the message says. See issue #262.
    • Receiver with Batch Send Mode JSON_ARRAY or XML_LIST and Enable JSON Schema Validation switched on: the JSON Schema no longer stops the channel. A batch is always sent without validation, but the schema was still compiled, so one that did not compile (for example with an invalid pattern) failed every batch with "init failed", and an empty schema or one that was not valid JSON was rejected at deployment. In batch mode the schema is now neither checked at deployment nor compiled, and instead of a warning for every message the deployment logs producer.config.ineffective once as ERROR. With Batch Send Mode NONE nothing changes. See issue #263.
    • Settings that deployed but made every poll, send, dead letter or Schema Registry call fail are now rejected at deployment, in the message form '<UI label>' (<parameter>) must …, got: <value>: on the receiver, Max Request Size (KB) or Buffer Memory (KB) below 1, a negative Producer Batch Size (KB) (0 still switches batching off), and with Avro serialization a Schema Registry URL that does not start with http:// or https://, such as sr.example.com:8081; on the sender, a Dead Letter Topic that Kafka refuses as a topic name (it takes 1 to 249 characters from a-z, A-Z, 0-9, ., _ and -, but not . or .. alone), such as orders dlq, and with Avro deserialization the same Schema Registry URL check; in both directions, a Bootstrap Servers entry that Kafka cannot read as host:port, such as broker1, or whose port is above 65535, and with a SASL Security Protocol a SASL Mechanism other than PLAIN, SCRAM-SHA-256 or SCRAM-SHA-512, which got the PLAIN login and failed at the first connect. The receiver editor now also refuses the three sizes below their minimum. Some values that failed before now work, mostly externalized ones that bypass the dropdowns: Kafka's keywords for Auto Offset Reset, Compression Type and Acknowledgments in another letter case, such as LATEST, GZIP or ALL, are passed in Kafka's spelling, and anything else, such as by_duration:PT1H, unchanged; TopicNameStrategy is accepted in any letter case, at deployment and for every message; spaces around a number, a switch, a credential alias, the Bootstrap Servers and the Schema Registry URL are removed, and so is an empty entry in Bootstrap Servers, such as after a trailing comma, which the Kafka client rejected. The Consumer Group ID and the Transactional ID Prefix keep their exact value. An empty Security Protocol connects with PLAINTEXT, without TLS and without authentication; this is now logged once at deployment as ERROR (consumer.config.ineffective or producer.config.ineffective), and the channel still starts. Rollout note: the new checks apply to every deployed channel at its next start, whatever its metadata version. Each rejected value failed at its first use, but a sender with such a Dead Letter Topic processes its records normally until the first one has to be dead-lettered; that record's DLQ write fails and blocks its partition. Such a channel now stops at its next start, until the topic name is fixed. See issue #261.
    • Sender with Avro: a Schema Registry that cannot serve a record's schema no longer sends the record to the DLQ or skips it. If the registry does not answer (refused connection, TLS failure, timeout) or answers 401, 408, 429 or 5xx, the record is not at fault: its partition now waits at the record and retries it with the usual backoff, with or without a DLQ and whatever Error Handling says, while other partitions keep flowing. Up to 1.4.1 an outage while the schema cache was cold, for example after every restart, wrote every record with a schema ID not fetched yet to the DLQ as DESERIALIZATION (with Skip Failed Message: skipped it), so valid records had to be replayed by hand. After this update a registry outage holds the affected partitions instead of filling the DLQ, and a rejected Schema Registry login (401) holds them until the credential is corrected and the integration flow restarted. A record that is not in the Confluent wire format, or whose schema ID the registry does not know (404), still goes to the DLQ. The same failures also count as transient for Retry Transient Errors Only and for the retryable field of adapter.failure.reported. See issue #188.
    • Sender with Batch Mode XML List (XML_LIST): a key or value with a character that XML 1.0 does not allow, such as the zero bytes of a Confluent header in front of a JSON value, made the whole batch unreadable as XML (An invalid XML character (Unicode: 0x0) was found in the CDATA section). Such a key or value is now written as Base64 of its UTF-8 bytes and marked format="base64"; so is such a field in Avro output as XML (avroOutputFormat XML). These are the control characters below U+0020 except tab, line feed and carriage return, and U+FFFE and U+FFFF. The receiver's XML List decodes format="base64" again, so a batch from the sender can be sent on unchanged; it also decodes a <key> or <value> that an integration flow marks format="base64" itself. See issue #284.

    Security¶

    • The LZ4 codec is now at.yawk.lz4:lz4-java 1.11.4, the maintained fork that kafka-clients 4.3.1 depends on, embedded in the adapter bundle. Up to 1.4.1 the adapter shipped org.lz4:lz4-java 1.8.0, which is affected by CVE-2025-12183 (out-of-bounds memory operations), CVE-2025-66566 (information leak in the safe decompressor) and CVE-2026-106451 (the native library is extracted to a predictable file in the temporary directory, where another local user can replace it). According to the advisories, a crafted LZ4-compressed batch on a topic that a sender reads could crash the worker's JVM or put stale memory contents into a message. kafka-clients 4.3.1 asks for the fork's 1.10.2, which is still affected by CVE-2026-106451 and five lesser advisories, so the adapter declares 1.11.4. Inside the adapter bundle lz4 now runs its pure Java safe implementation (lz4Implementation=JavaSafe in class-warmup.codecs.completed) instead of JavaUnsafe. See issue #240.
    • SASL credentials: a password with a line break no longer puts a part of itself into the trace and the message processing log. The line break ended the quoted value in the Kafka client's JAAS configuration, so every connect failed with Value not specified for key '<the text after the line break>' in JAAS config, and that text appeared in producer.init.failed, consumer.init.failed or dlq.producer.init.failed and, on the receiver, in the error of every message. The receiver, the sender and the DLQ producer now refuse a user name or password with a line break (CR or LF) before the Kafka client sees it, with a message that names the alias and never the value: The password stored under 'Credential Alias' (credentialAlias) '<alias>' contains a line break, … (DLQ SASL Credential Alias for the DLQ producer). The channel still cannot connect until the credential is stored without the line break. Every other character, a tab or another control character included, still reaches the broker unchanged. See issue #245.
    • Receiver: the exchange headers Authorization, Proxy-Authorization, Cookie and Set-Cookie are no longer written to Kafka through a wildcard in Allowed Headers (allowedHeaders), the default * included. A flow that had set an access token for an earlier HTTP call, for example in a Content Modifier, wrote it into a header of every record, readable by everyone with read access to the topic. A pattern that names such a header exactly still sends it (*|Authorization). This changes the behaviour of every adapter line from 1.0 to 1.4 without an "Update Version" click: a credential in a topic is a security problem, and a flow that forwards such a header on purpose keeps it by naming the header. Other headers are not affected; SAP_* headers are still sent with *. See issue #195.

    [1.4.1] - 2026-10-06¶

    Fixed¶

    • The receiver's single-message retry (producerRetryMaxAttempts > 1, no batch mode) could write a record twice. It repeated a send whose record was already in the producer's buffer — after a delivery timeout or a dropped connection the record may already be on the broker, and the broker only deduplicates the client's own retries of the same batch, not a new send. A send is now only repeated when the record provably never reached the buffer (metadata wait, full buffer, the KAFKA-10902 monitor fault); otherwise the message fails with stopReason=OUTCOME_UNKNOWN. Single-message retries therefore recover fewer failures than before, as the tooltip always promised. See issue #184.
    • Numbers in JSON_ARRAY batch output (sender) and in records produced from a JSON_ARRAY batch (receiver) now keep their trailing zeros and precision: 100.00 became 100.0, 12345678.90 became 1.23456789E7, and digits beyond double precision were lost. Values are unchanged. Numbers are still written in canonical decimal form, so exponent input and decimals below 0.000001 come out in E-notation (1e3 → 1E+3, 0.0000001 → 1E-7). A sender value that is JSON followed by more text ({"a":1}garbage, true story) is now embedded as the full string instead of being cut after the first JSON value, an empty value stays "" instead of becoming null, and a receiver JSON batch with content after the array is rejected. See issue #181.
    • XML_LIST batches on the receiver are read one level deep: <record> only as a direct child of <kafkaRecords>, and <key>, <value> and <headers> only as direct children of <record>. A <record> or <key> inside a value was taken as an extra record or as the partition key. A batch that wraps its records in an intermediate element is no longer accepted; the error says that <record> must be a direct child of <kafkaRecords>. See issue #181.
    • Sender channels whose configuration could never work now fail at deployment with a message naming the field, instead of looping at runtime: an empty Consumer Group ID, an unknown Offset Commit Strategy (which never committed and redelivered everything), Max Poll Records below 1, a negative Fetch Min Bytes, Fetch Max Wait (ms), Poll Timeout (ms) or Max Retries before DLQ, Max Records per IFlow Run (MPL) below 1 in batch mode, and a Dead Letter Topic that is also a source topic (an endless fail-and-reconsume loop) or has spaces around its name. The messages give the UI label and the parameter name. Each check applies only where the field is in effect, so for example a legacy SPLIT_EXCHANGES channel with a stale Max Records per IFlow Run still starts. Unknown Batch Output Format or Avro Output Format values keep their JSON fallback and are now reported once at ERROR, and a Consecutive Error Threshold or Initial Pause Duration (sec) below 1 is used as 1 (a pause of 0 never paused). Rollout note: the checks apply to every deployed sender channel at its next start, whatever its metadata version; only channels that were already broken are affected. See issue #183.
    • The sender's DLQ producer rejected records above 1 MB (RecordTooLargeException) although the consumer fetches up to Max Fetch Size per Partition (KB) (50 MB), and blocked 60 s per record when the DLQ topic was missing. It is now sized for the configured fetch size plus 1 MB for the error headers and waits at most 15 s. The fetch size is a soft limit on compressed bytes, so a single larger record can still be rejected. See issue #183.
    • Receiver channels whose configuration could never work now fail at deployment with a message giving the UI label and parameter name: an unknown Batch Send Mode, Delivery Timeout (Seconds) below 1 (every send failed), and a Subject Name Strategy other than TopicNameStrategy with Avro serialization (every message failed). In both directions, empty Bootstrap Servers and a JSON Schema that is not valid JSON (while Enable JSON Schema Validation is on) are rejected at deployment; the schema is only parsed, not compiled, so no remote $ref is fetched. Rollout note: applies to every deployed channel at its next start, whatever its metadata version; only channels that were already broken are affected. See issue #183.
    • A Schema Registry credential alias that could not be resolved was silently ignored: the channel connected without authentication, and against a registry that requires it every record failed with HTTP 401, which looked like bad data. The Avro helper now fails with a message naming the alias — on the sender at the first connect, on the receiver at the first send, not at deployment. Rollout note: this also affects a channel whose registry needs no authentication but which still carries an alias that is not deployed on this tenant (common after copying an iFlow); it worked before and now fails. Clear the field in that case. Outside CPI, where no secure store exists, the alias is still ignored. See issue #183.

    [1.4.0] - 2026-10-03¶

    Added¶

    • Sender option Error Handling (errorHandling, metadata version 1.4) decides what happens to a message whose processing fails while no Dead Letter Queue is enabled. It mirrors the option of the same name in SAP's Kafka sender adapter. Retry Failed Message (default) retries the same offset until it succeeds: the partition waits, the retries back off from Retry Delay (at least 1 second) doubling up to 5 minutes, and nothing is lost. Skip Failed Message continues with the next offset (at-most-once). It applies to failed IFlow calls, batches that cannot be formatted and records that cannot be deserialized; JSON Schema-invalid records stay dropped without a DLQ, as documented. In batch mode the whole failed batch is retried; only a DLQ isolates a single bad record. Retry Delay is now also shown without a DLQ, in a new Failed Messages group. See issue #187.

    Changed¶

    • Without a DLQ, failed messages are now retried instead of skipped. Until now a sender channel without a DLQ skipped every message whose IFlow processing failed, although the documentation promised redelivery. The new default Retry Failed Message retries it. Rollout note: this applies to every sender channel without a DLQ as soon as this adapter version is deployed, also to iFlows that stay on an older metadata version (1.0 to 1.3) and therefore have no Error Handling field in their UI. A message that can never be processed now holds up its partition until the cause is fixed, instead of being dropped. With Auto-Pause on Errors enabled, every retry counts as a failure, so such a message pauses the whole consumer; use a DLQ for flows where single bad messages occur. To keep the old behaviour, update the channel to version 1.4 (Update Version) and select Skip Failed Message. See issue #187.
    • The sender's start checks no longer reject values in fields that have no effect: the drain fields while drain is off, and Retry Delay while neither a DLQ nor Retry Failed Message uses it. See issue #174.
    • SASL Mechanism is now shown only for the security protocols SASL_SSL and SASL_PLAINTEXT (metadata version 1.4). With SSL or PLAINTEXT the runtime never read it. See issue #179.
    • The security protocol SSL is now labelled SSL (TLS, client certificate optional via Keystore Alias). The old label SSL (TLS, certificate authentication) suggested a client certificate was required; without an SSL Keystore Alias the channel uses TLS without client authentication. See issue #179.
    • The receiver's Delay Between Attempts and Total Retry Budget are now hidden while Max Send Attempts is 1 (metadata version 1.4): the retry is off, and the start check already ignores both fields then. See issue #207.
    • The UI now flags a value outside the allowed range in five fields (metadata version 1.4): sender Max Fetch Size per Partition (KB) (1–51200) and Retry Delay (0–300), receiver Max Send Attempts (1–5), Delay Between Attempts (1–30) and Total Retry Budget (5–900). These are the ranges the start check already enforces whenever the field is in effect; the only value newly flagged is an out-of-range Retry Delay on a sender with Skip Failed Message and no DLQ, where the field has no effect. An externalized {{parameter}} is not flagged. See issue #186.
    • Sender channels on 1.0 or 1.1 cannot be updated to a newer version with Update Version; they have to be deleted and recreated. Their metadata still offers Individual Exchanges (SPLIT_EXCHANGES) for Batch Output Format, which 1.2.0 removed, and CPI refuses an update that drops a fixed value, whatever the channel stores. Existing channels keep running unchanged. Receiver channels and sender channels from 1.2 on are not affected. VERSIONING.md now requires every minor line to keep the fixed values of the lines before it. See issue #219.

    Fixed¶

    • Tooltips on the 1.4 metadata (and the matching documentation) that promised behaviour the adapter does not have: Report Validation Failures means a failed MPL entry on the sender but only a payload trace on the receiver, where an invalid message always fails; receiver JSON Schema validation is skipped in batch mode; only TopicNameStrategy works for Avro serialization; transactions apply to the batch send modes only; the idempotent producer forces acks=all and is not end-to-end exactly-once; the DLQ credential alias writes to the same cluster; the receiver topic accepts ${…} expressions; the receiver's Write MPL Error Attachment currently has no effect; Total Retry Budget now states the real worst-case formula. The sender's Batch Output Format no longer mentions the removed Individual Exchanges. See issue #179.
    • A sender channel with Report Validation Failures in CPI Monitoring could still log a false consumer.mpl.report.failed ERROR for every invalid record when the runtime rethrows the expected validation failure wrapped in another exception. The check now follows the cause chain. Follow-up to issue #177.
    • A Schema Registry URL saved with credentials but without a scheme (user:password@host:8081) was written to the log unmasked. The credentials are now masked with or without a scheme. Follow-up to issue #177.
    • A sender channel with Avro deserialization replaced its Schema Registry client on every reconnect without closing the old one and lost its schema cache. It now keeps one for the life of the channel; as a consequence, the Schema Registry credential alias is read when the channel starts, so a rotated credential takes effect at the next deploy or restart. Follow-up to issue #171.

    [1.3.7] - 2026-10-01¶

    Fixed¶

    • With producerBatchMode set to JSON_ARRAY or XML_LIST, the receiver channel never wrote the sent payload to the message processing log trace; only failures were traced. Batch sends now write one RECEIVER_OUTBOUND trace per message before the send, as single-message mode does, in the plain and the transactional path. The trace holds the batch as received, before Avro or Schema Registry serialization. See issue #166.
    • On a receiver channel with Avro value serialization, every message after a producer rebuild went out as plain JSON, with CpiKafkaPlusStatus=OK and a producer.rebuild.effect outcome=RECOVERED line in the trace, until the integration flow was redeployed. A rebuild (after an authentication or authorization error, a rotated SASL secret, OutOfOrderSequenceException, a stalled send, or KAFKA-10902) discarded the Avro serializer along with the producer, and nothing created it again. A rebuild now replaces only the producer. A send that finds Avro configured but no serializer fails instead of sending the raw body. A transactional batch whose serializer cannot be created, for example because the Schema Registry credential cannot be read, now fails the message instead of committing it as JSON. A second defect in the same code: a rebuild racing a concurrent send could leave the channel marked ready without a producer, so every message failed with "Kafka producer not initialized" until the flow was restarted. The producer is now swapped under the initialization lock and closed outside it. See issue #169.
    • In a non-transactional batch, a record that failed to serialize (typically an Avro schema mismatch) left the records before it buffered in the producer. The rebuild that followed flushed them to Kafka although the message failed, so a retry wrote them a second time. All records of a batch are now serialized before the first is sent, so a serialization error writes nothing. Serialization errors are now reported as data errors (KP-PROD-004) and no longer rebuild the producer. See issue #170.
    • On receiver channels with an SSL keystore alias (mTLS), the topic probe that runs before a send could not be created. It copied only the ssl.*, sasl.* and security.protocol settings and dropped the keystore alias, so the adapter's SSL engine factory refused to start. Every probe was inconclusive: a missing topic, a rejected certificate or failed authentication surfaced only as a metadata timeout, every send failure carried the note "The broker could not be reached during the pre-send check", and each message paid for a failed client construction and a WARN line. The probe now carries the alias. Behaviour change: on these channels a send to a topic that does not exist now fails right away, even when the broker would auto-create the topic. This is the documented behaviour and matches channels without a keystore alias. See issue #180.
    • On sender channels with a Dead Letter Queue, every consumer reconnect (after repeated poll failures or a fenced static member) created a new DLQ producer and never closed the old one. Each leaked producer kept its network thread, a broker connection and its JMX registration, and fencing loops leaked one every 40–130 seconds. The DLQ producer now survives reconnects; it already rebuilds itself when it breaks. See issue #171.
    • A lower-case Security Protocol or SASL Mechanism, which only an externalized parameter can deliver (the UI offers fixed values), broke the connection silently: sasl_ssl set neither the SASL mechanism, the JAAS login nor the keystore alias, and ssl ignored the keystore alias and used the JVM truststore. Both values are now trimmed and upper-cased. Receiver sizes and timeouts large enough to overflow int were wrapped instead of capped: a Max Request Size of 4,194,304 KB became 0 bytes and 5,242,880 KB became 1 GiB, and a very large Delivery Timeout turned negative. They are now computed as long and capped at the largest int. Batch Size is also capped at Buffer Memory: a batch has to fit into the buffer, and a larger value made every send fail. See issue #175.
    • The receiver's start checks rejected channels because of fields that have no effect. With the retry off (Max Send Attempts 1), an out-of-range Retry Delay or Retry Budget still blocked the deployment. On a batch channel without transactions, where retry never applies, the retry's worst case was still held against the budget. And Enable Transactions with Batch Mode NONE, where single messages always go through the non-transactional producer, still demanded a transactional ID prefix and a delivery timeout of at most 870 seconds, and was judged by the much longer transactional worst case. All three now deploy. The last case logs producer.config.ineffective once, and its producer no longer gets a transaction.timeout.ms it never uses. See issue #174.
    • Log hygiene. Every record that failed JSON Schema validation with Report Errors on also logged a misleading ERROR consumer.mpl.report.failed, although writing the failed message was exactly what happened. That line is gone. The receiver's deployment-time findings, a missing topic and an unreachable broker, were logged at WARN, which never reaches the tenant trace; they are now ERROR lines (producer.start.topic.missing, producer.start.broker.unreachable), once per start. A Schema Registry URL with user:password@ was logged in full when the Avro helpers started; the credentials are now masked as ***@. Stale code comments and option descriptions were corrected (no cluster lock is requested, batchTimeout is the poll timeout, the DLQ credential alias addresses the same cluster, the per-direction meaning of jsonSchemaReportError), and two unused constants were removed. See issue #177.
    • The sender lost records whose dead-letter write failed. poll() moves the consumer past every record it returns, and the adapter only kept the highest processed offset per partition, so the next successful record of the partition committed over the failed one. The trace even said consequence="offset not committed, record will be reprocessed", but the record was never delivered again. The adapter now tracks every record of a poll. A partition is committed only up to its first open record, and every partition is rewound to that record after the poll. A record whose dead-letter write fails blocks its partition: nothing after it is processed or committed, and it is retried after a backoff of 1 second, doubling up to 5 minutes. The other partitions keep flowing, and the trace shows consumer.partition.retry. This covers failed IFlow processing, failed deserialization and failed JSON Schema validation alike. A Throwable that escapes the adapter itself no longer skips the rest of its poll either: the record is retried. Without a DLQ, a record whose IFlow processing fails is still skipped as before, but now only that record, not the rest of its poll. See issue #187.
    • With JSON Schema validation in batch mode, an invalid record's offset was committed before the batches of its partition ran. If an earlier batch then failed or the node went down, the records before the invalid one were lost even after a restart. The filter no longer commits; invalid records are committed together with the batches around them. An Avro deserialization failure inside the filter escaped the poll and bypassed the DLQ; it now takes the regular dead-letter path. See issue #173.
    • A failing offset commit was treated as a failed record. A WakeupException from the undeploy, an interrupt, or a commit timeout sent a successfully processed record (or batch) back through the retries and into the DLQ, or produced a failed message processing log, on every undeploy under load. The commit now runs outside the route's error handling. A wakeup or interrupt stops processing and leaves the offset pending for the revoke commit; any other commit error keeps it pending for the next commit. An interrupted retry delay no longer dead-letters the record either. See issue #172.
    • Auto-pause never paused on failed IFlow calls, the case it is recommended for. Route failures are handled inside the adapter and never surfaced as exceptions, so every poll reset the failure counter, even when every record failed. Failures are now counted per poll, including records that end up in the DLQ, and only a successful IFlow call resets the counter. Flows with auto-pause enabled now pause during a backend outage, as documented. See issue #182.

    Fixed¶

    • Every adapter update lost the messages of every running Kafka integration flow on the tenant until the flow was redeployed. Deploying a new adapter version makes CPI purge the old bundle revision immediately, while the running routes keep its class loader; the next class or resource that had never been loaded before then fails (NoClassDefFoundError … bundle wiring … no longer valid on the first LZ4 batch or on close(), SnappyError FAILED_TO_LOAD_NATIVE_LIBRARY on the first snappy batch) and stays failed, because HotSpot caches the resolution failure. The adapter's own reaction made it worse: rebuilding the consumer and restarting the Camel route re-used the same dead class loader, so it looped every ~6 s and never left the consumer group cleanly. The adapter now pre-loads its whole class space once per bundle revision when the first endpoint starts — its own classes synchronously, one compress/decompress round trip per codec so the snappy/zstd/lz4 native libraries are extracted while the revision is live, and every remaining class on a low-priority daemon thread (~6,900 classes, ~2 s on a tenant, finished before the first partition assignment) — and reports it as class-warmup.*. Verified on a tenant by updating the adapter under a running flow and then sending LZ4 and snappy batches and undeploying the flow: no failure, clean LeaveGroup. On the send side there is no polling loop to stop, so every exchange that hits the dead class space now fails with an IllegalStateException naming the cause and the remedy ("Redeploy the integration flow …") instead of a generic send error, and the trace carries one send.bundle-wiring-invalid line per minute. The bundle declares DynamicImport-Package: *; Camel, the SAP APIs, SLF4J and the javax.* packages are therefore wired on first reference. A reference that had never been reached while the revision was live — typically a Camel exception type or a helper on an error or stop path — went through the purged revision's wiring and failed with the same bundle wiring … no longer valid error that #148 fixed for everything inside the bundle. The warm-up now has a third stage: it reads the constant pool of every class the bundle ships and pre-loads the 220 classes that the bytecode references but the bundle does not contain, so nothing is left to resolve over a wire that an update can invalidate.     [1.3.0] - 2026-08-20¶

    Added¶

    • The receiver direction can now repeat a failed send with a brand-new producer (producerRetryMaxAttempts, default 1 — off). Kafka's own retries and delivery.timeout.ms only repeat inside one producer instance, so after a NetworkException: Disconnected from node 3 the transactional producer is left in a state where nothing on it can succeed and the send fails after roughly 400 ms with no second chance; only a throw-away producer recovers from that. The core of the feature is what it refuses to do: an attempt is only repeated where the previous one provably wrote nothing. A transactional batch that failed before the commit qualifies — the aborted transaction is invisible to read_committed consumers, and the successor producer with the same transactional.id fences the old epoch. A failure inside the commit does not, and never will: KafkaProducer.close() aborts an ongoing transaction only "if it's not already completing" and initTransactions() "awaits its completion" of a commit that has begun, so the batch does get committed and a retry would write it twice. That is documented client behaviour, not a residual risk, so the transaction phase is tracked explicitly and the loop stops with stopReason=COMMIT_OUTCOME_UNKNOWN. A non-transactional single message is repeated on the same producer, because the broker deduplicates on (PID, sequence) and a fresh producer would get a new PID; without enableIdempotence it is not repeated at all rather than silently duplicated. A partially sent non-transactional batch is never repeated, and configuring the retry on such a channel now says so at start-up instead of doing nothing. The parameters are deliberately separate from the consumer's retryDelaySeconds / retryOnlyTransientErrors, which carry exponential-backoff semantics — one option meaning two things depending on channel direction is a support trap. The delay is constant with a one-second floor, because the client has already exhausted an exponential backoff and three sub-second retries only hammer the node that just disappeared. producerRetryTotalBudgetSeconds (default 30 s) bounds all attempts of one message together, and a start-up check rejects a configuration whose worst case cannot fit inside it — the arithmetic is roughly four times deliveryTimeoutSeconds per transactional attempt, not once, because initTransactions(), the metadata block in send() and commitTransaction() are each bounded by max.block.ms on top of the wait for acknowledgements. A retry that could never reach its second attempt is a promise to operations that would only be discovered during the outage it was configured for. Every attempt is reported at ERROR — WARN and INFO never reach the tenant trace, the same invisibility defect fixed in a dozen places in 1.2.7 — via producer.retry.attempt, producer.retry.effect, producer.retry.exhausted and producer.retry.skipped, with effect and exhausted sharing attempts and recovered so "how often does the retry actually rescue a message" is a ratio of two greppable lines. The failure handlers still fire exactly once per message, so three attempts do not count as three failures against the auto-pause and node-fault escalation thresholds. The retry history appears in the MPL status text and attachment, a successful recovery is filterable in Message Monitoring via KafkaRetryAttempts, and the iFlow sees CamelKafkaPlusRetryAttempts.
    • The outer retry treats the KAFKA-10902 monitor fault as retriable even under the default producerRetryOnlyTransientErrors=true. IllegalMonitorStateException: current thread is not owner matches no Kafka exception hierarchy, so the classifier reports UNKNOWN_FATAL and the retry would have refused the one failure it was built after — a production trace from 2026-08-20 shows it on two channels of one tenant, in bursts on individual worker nodes, while the same broker served everything else. The classifier has no category for a defect in the client itself, and treating "I do not recognise this" as "the broker has ruled" is how a retry ends up declining the case it exists for. Retrying cannot duplicate: before the commit the failed attempt's transaction is aborted and invisible to read_committed, and on the single path idempotence is a precondition so the broker deduplicates on (PID, sequence). The exemption is narrow on purpose — it needs a Kafka frame in the stack trace, and it does not reach past the phase rule, so a monitor fault inside the commit still stops with COMMIT_OUTCOME_UNKNOWN. It remains a second line of defence behind the metadata pre-warm and the raised metadata.max.idle.ms, which are what keep the client out of the defective path.

    Fixed¶

    • abortTransaction() after a failed transactional batch has been replaced by a bounded close(). After a network disconnect the abort throws itself — it is exactly the broken state it was meant to clean up — and the suppressed exception it added obscured the original cause. close(Duration) aborts an ongoing transaction that is not already completing, and the next producer with the same transactional.id cleans up whatever is left, so the explicit abort bought nothing.
    • The consumer's liveness heartbeat was written to the tenant trace file at ERROR every 5 minutes, roughly 288 red lines per day and endpoint that reported only that nothing had happened. The recurring reason=INTERVAL tick is now INFO; the reason=STATE_CHANGE line stays at ERROR because it reports an event rather than a pulse and is bounded. The tick proves only that the scheduler called poll() — not a failure anyone investigates, since an unreachable broker, a rejected credential, a rebalance storm and a stalled partition each already emit their own ERROR — and it cannot even be absent when it matters, because it keeps reporting "alive" while a partition does not advance. At ERROR it therefore bought no evidence while competing with real failures for attention in a file shared with every other integration flow on the tenant. Before 1.2.7 it fired once per poll cycle, where it was every single line the adapter contributed.
    • Closing the consumer for a reconnect was logged at WARN, which does not reach the tenant trace file, and the rebuild that follows logs at INFO. A consumer being destroyed and recreated therefore left no visible record at all and was indistinguishable from one that had simply gone quiet — the same WARN-invisibility defect fixed in three other places in 1.2.7. Now ERROR, keeping consecutiveFailures, durationMs and reason.
    • The consumer was destroyed and rebuilt on every failed poll once an outage passed the fifth consecutive failure. Neither the failure counter nor the duration window was reset when a reconnect fired, so both thresholds stayed exceeded for as long as the outage lasted — a rebuild storm of the same shape the shared producer was rate-limited against in 1.2.7, only unbounded, and with a 15-second polling interval it meant a fresh KafkaConsumer every 15 seconds for the whole outage. Both counters now reset on reconnect, so they measure failures since the last reconnect and a rebuild happens at most once per five polls or once per 60 seconds.
    • Removed an orphaned Javadoc block above logEmitCycleHeartbeat() that still described runEmitCycle(), from which the method had been extracted.
    • Consumer poll failures caused by stale OSGi class wiring after hot runtime updates (for example NoClassDefFoundError / ClassNotFoundException with bundle wiring ... no longer valid) now trigger an immediate consumer rebuild instead of waiting for generic reconnect thresholds, and class resolution now falls back to the thread's original context class loader before the system class loader. If wiring is still stale, the adapter now additionally performs a bounded automatic restart of the affected Camel route (max 2 attempts, 15-minute cooldown), mirroring the manual iFlow restart recovery without requiring customers to restart every consumer route themselves.
    • MPL error diagnostics now include the full Java stack trace in both trace messages and KafkaAdapterError attachments (instead of a bounded top-stack summary), attachment writing is configurable via writeMplErrorAttachment (default true) on both sender and receiver channels, and successful DLQ routing is now written directly into the MPL status text (moved to dead-letter topic ...) so the outcome is visible without opening attachments.

    • A dead-letter producer that became unusable stalled the consumer indefinitely. That is worse than it sounds: the dead-letter send is what permits the offset commit, so a failing send meant no commit, the same record polled again forever, and every later message blocked behind it.     • Adapter failure lines now carry the identifiers that tie them to one integration-flow message: mplId (SAP_MessageProcessingLogID), applicationId and exchangeId. The tenant trace format reserves four correlation fields per record and all four were empty on every adapter line in the analysed corpus, so a failure could be seen but not attributed to a message, a sender or a payload.
    • The producer now avoids the KAFKA-10902 code path instead of only recovering from it. KafkaProducer.waitOnMetadata() blocks in the defective ProducerMetadata.awaitUpdate() only when a topic's partition count is missing from the client's metadata cache, so two changes keep it present: the metadata for each topic is fetched once up front, before any record is submitted, and metadata.max.idle.ms is raised from the client default of 5 minutes to 1 hour. That default mattered more than it appears — it discards the metadata of a topic that has not been produced to for five minutes, so an integration flow producing less often than that entered the vulnerable blocking path on every message. Freshness is unchanged, being governed by metadata.max.age.ms, whose refresh runs on the client's network thread and does not block senders. A failed pre-warm never fails the exchange.
    • The producer now survives KAFKA-10902, an open, unfixed defect in the Kafka client that is present in the embedded kafka-clients version. ProducerMetadata.awaitUpdate is synchronized and hands this to SystemTime.waitObject, which re-enters the same monitor and calls Object.wait() at recursion depth 2; when the thread loses ownership the send fails with IllegalMonitorStateException: current thread is not owner. A synchronous failure of that kind is retried, which provably cannot duplicate a record: KafkaProducer.doSend() calls waitOnMetadata(...) before accumulator.append(...), so the record never entered the accumulator. Retrying is bounded three ways and the first bound reached stops it — at most 3 retries per record, at most 5 across an entire batch regardless of record count, and never past the existing batch deadline. Worst case is 5 extra attempts and about 250 ms per batch. Every outcome is logged, including successful recovery, with retryOutcome, retryCount, batchRetriesLeft and stopReason.

    • Fixed silent message loss when an iFlow swallowed a processing error internally — for example via an exception subprocess, or an Error End event in a sub-iFlow called with ProcessDirect.     • Updated kafka-clients 3.9.1 → 3.9.2.
    • Updated Jackson (core/databind/dataformats/datatypes) 2.16.0 → 2.22.0.
    • Updated test dependency commons-lang3 3.14.0 → 3.20.0.

    Fixed¶

    • Restored CPI-compatible LZ4 compression after the Kafka 3.9.2 bump: excluded the at.yawk.lz4:lz4-java fork (broken OSGi manifest that fails the CPI OSGi resolver) and pinned the well-behaved org.lz4:lz4-java:1.8.0, embedded in the fat bundle.

    Added¶

    • maven-enforcer build guard that fails early if a known CPI-incompatible transitive dependency is pulled in.
    • ESA content check in the preview build: fails if any stray standalone jar escapes the fat bundle.
    • Dependabot configuration for Maven and GitHub Actions (Camel excluded — provided by CPI).

    [1.0.3] - 2026-07-02¶

    First public release.

    Added¶

    • Kafka Sender adapter (Consumer → CPI) and Kafka Receiver adapter (CPI → Kafka Producer).
    • Batch processing in JSON_ARRAY, XML_LIST and SPLIT_EXCHANGES modes.
    • Avro / Confluent Schema Registry serialization and deserialization.
    • Security: SASL/PLAIN, SASL/SCRAM, SSL/TLS and mTLS.
    • At-least-once delivery via manual offset commit after successful processing, with durable per-partition offset tracking that survives consumer-group rebalances.
    • Dead Letter Queue routing for deserialization / poison-pill failures.
    • CPI MPL tracing and IFlow connection-status monitoring.
    • Configurable polling with rebalance-safe consumer-group handling.
    • Header-based routing — dynamic topic, key and partition override via exchange headers.
    • Semantic adapter versioning aligned with SAP CPI's compatibility model.
